# horizon-essentials: the team handbook

A GPL-3.0 port of **EssentialsX** to **Horizon** (Minecraft Java 26.3 rewritten in Rust) as a *native mod*:
horizon-mixins injects our Rust modules and hooks into a pinned Horizon source at build time, and we compile our
own dedicated server. **Unmodified vanilla 26.3 clients must be able to use every feature**, so we only use
vanilla mechanics: commands, chat/system messages, vanilla blocks, items, containers and packets.

The goal is `PARITY.md` at 100%: every command and feature done, or `partial` with the reason and a test.

## Ground rules

- **Behaviour = EssentialsX's.** Read the Java before you write Rust (it is GPL-3.0, so is this repo):
  `~/Projects/horizon-mods/EssentialsX/Essentials/src/main/java/com/earth2me/essentials/`
  (`commands/Command<name>.java`, `User.java`, `UserData.java`, `Settings.java`, `Teleport.java`, `Kit.java`,
  `signs/`, `Jails.java`, `textreader/`, `utils/`), the modules (`EssentialsChat/`, `EssentialsSpawn/`,
  `EssentialsProtect/`, `EssentialsAntiBuild/`, `EssentialsDiscord/`, `EssentialsDiscordLink/`, `EssentialsXMPP/`,
  `EssentialsGeoIP/`), and `Essentials/src/main/resources/{config.yml,messages.properties,plugin.yml}`.
  Same message keys (`ess.tl("homeSet", ...)`), same config keys, same permission nodes, same userdata keys.
- **Tests first.** Phase 1: failing tests for every row of your PARITY section. Phase 2: make them pass.
- **Stay in your lane.** You own:
  - `mixins/ess-<area>/` (your logic module, your glue, your hooks, your `horizon-mixin.toml`);
  - your block in `crates/ess-standalone/src/game/mod.rs` (one line per module you add);
  - your region (`// ---- area <area> ----` … `// ---- end <area> ----`) in `mixins/essentials/ess_core.rs`
    (Host trait), `ess_testkit.rs` (FakeHost fields, init, impl) and `ess_glue.rs` (delegations);
  - `tools/e2e/scenarios/<area>_*.py`;
  - your section of `PARITY.md`.
  Anything else in `mixins/essentials/` is the core: don't edit it. If you need a core change (a new event
  kind, a dispatcher change), write it in `mixins/ess-<area>/CORE-REQUESTS.md` and work around it meanwhile.
- **Never** edit the Horizon checkout or `target/mixins/*` by hand; never commit game files, binaries or
  `target/`. Don't touch `~/.local/share/horizon*` (the e2e runner uses scratch homes).
- **Git:** work on your branch in your worktree. Commit often; every commit message ends with
  ```

  Claude-Session: https://claude.ai/code/session_013GDYUAVaRDM8xjbypsA8iQ
  ```
  No pushes, no merges, no rebases of others' work: the lead merges.

```

  ess_core.rs             Ess (config, users, perms, scheduler, dispatcher, events), Host trait, Loc/Item/Sender...
  ess_text.rs             MiniMessage -> spans, MessageFormat, legacy & codes
  ess_yaml.rs             YAML read/write (config.yml, userdata, kits.yml...)
  ess_meta.rs  ess_messages.rs  ess_defaults.rs   GENERATED by `cargo run -p ess-gen` (plugin.yml, messages, default files)
  ess_testkit.rs          FakeHost + TestServer (tests only)
  ess_areas.rs            calls every area's register()
  ess_glue.rs             GameHost: Host over Horizon's Game/hub; command queue; tick
  hook_command.rs hook_tick.rs   the two base injections
mixins/ess-<area>/        one bundle per area: ess_<area>.rs (pure logic + tests), ess_glue_<area>.rs (Host
                          methods over Horizon), hook_*.rs helpers, horizon-mixin.toml (modules + injections)
crates/ess-standalone/    mounts the pure modules at crate::game::* -> `cargo test` without Horizon (L1)
tools/horizon.py          stage | check | build | test against the pinned Horizon (L2)
tools/ess-bot/            a scripted vanilla-protocol player
tools/e2e/run.py          real dedicated server + ess-bot players, scenarios in tools/e2e/scenarios (L3)
tools/ess-gen/            regenerates ess_meta/messages/defaults from EssentialsX
```

## How a feature is built

1. **Read** the EssentialsX command class(es) and the messages/config they use.
2. **Test (L1)** in your module's `#[cfg(test)] mod tests` with `crate::game::ess_testkit::TestServer`:
   ```rust
   let mut t = TestServer::with_config("teleport-delay: 0");
   let alice = t.join("Alice");
   t.op("Alice");                                   // vanilla op (gets op-default nodes)
   assert_eq!(t.cmd(alice, "/sethome base"), ["Home base set."]);
   t.host.p(alice).loc = Loc::new("minecraft:overworld", 100.5, 70.0, 5.5);
   assert_eq!(t.cmd(alice, "/home base"), ["Teleporting..."]);
   assert_eq!(t.loc(alice).x, ...);
   t.tick(20);                                      // scheduler, movement, tick listeners; +50 ms each
   ```
   `t.cmd` returns the plain text lines the player received (styles in `t.host.spans`); `t.console(..)`
   for the console; `t.host` is the FakeHost: inspect or set players, blocks, signs, entities, recorded
   vanilla commands (`console_commands`, `player_commands`), bans, time, weather...
   Test every alias you care about, permission branches (`t.permissions("groups: ...")`), config options
   (`TestServer::with_config`), and the exact English messages (from messages.properties).
3. **Implement** in `ess_<area>.rs`:
   ```rust
   pub fn register(ess: &mut Ess) {
       ess.register(Command { name: "sethome", run: sethome, tab: None,
           usages: &[("/<command> [[player:]name]", "sethomeCommandUsage1")] });
       ess.listeners.death.push(on_death);
   }
   fn sethome(ctx: &mut Ctx, args: &[String]) -> CmdResult {
       let player = ctx.player()?;                  // "only players" error for the console
       if args.is_empty() { return Err(CmdError::Usage(None)); }
       ...
       ctx.tl("homeSet", &[Arg::from(name)]);
       Ok(())
   }
   ```
   The command name must be the plugin.yml name: aliases and `e`-prefixes come from `ess_meta` automatically,
   and the dispatcher checks `essentials.<name>` before calling you (check sub-nodes yourself with `ctx.has`).
   Errors: `CmdError::Usage(None)` (NotEnoughArguments), `PlayerNotFound`, `Tl(key, args)` (shown inside
   `errorWithMessage`), `Quiet`. State: `ctx.ess.users.user(uuid).set("homes.base", loc.to_yaml())` (userdata
   YAML, same keys as EssentialsX), `ctx.ess.state::<YourState>()` for in-memory state, `ctx.ess.config_*`
   for config.yml, `ctx.ess.read_yaml("warps/x.yml")`/`write_yaml` for data files, `ctx.ess.scheduler.later`
   for delays. Use `Host` methods for everything about the server.
4. **Glue (L2)**: fill the bodies of your `ess_glue_<area>.rs` functions over Horizon (start from the hook
   and API notes below; read the pinned source in `target/mixins/pinned/crates/horizon-client/src/` after a
   stage). Add injections for events you own to your `horizon-mixin.toml` (helpers next to it, calling
   `crate::game::ess_glue::with_ess(game, |ess, host| ess.on_<event>(host, ...))`). Then
   `python3 tools/horizon.py check` and `python3 tools/horizon.py test`.
5. **End to end (L3)** for multi-player or protocol-visible flows: `tools/e2e/scenarios/<area>_<topic>.py`
   (see `smoke.py`: `t.bot("Alice")`, `bot.cmd`, `bot.expect(regex)`, `bot.expect_pos`, `t.console`).
6. **PARITY.md**: set the row's status and notes.

## Commands

```sh
cargo test -p ess-standalone                       # L1: seconds, no Horizon needed
cargo test -p ess-standalone ess_tp                # one area
export CARGO_BUILD_JOBS=3                          # 6 agents share 24 threads: keep this
python3 tools/horizon.py check                     # L2: stage + compile the modded server (first time ~1 min)
python3 tools/horizon.py test                      # L2: our unit tests inside the game crate
python3 tools/horizon.py build                     # the server: target/horizon-cargo/fast/horizon-client (first time ~8 min)
cargo build --manifest-path tools/ess-bot/Cargo.toml --target-dir target/ess-bot   # after a stage
python3 tools/e2e/run.py <area>                    # L3 scenarios (needs build + ess-bot); --keep keeps failures
cargo run -p ess-gen                               # lead only: regenerate data from EssentialsX
```
The prepared game files for L3 come from `~/.local/share/horizon-launcher/server-runtime/game-files/horizon-client/26.3`
(read-only; never copy them into the repo).

## Horizon facts you will need

- **Execution model.** Player commands are claimed in `native_command` and run in the next `native_tick`
  through `Ess::dispatch`, with every player in the hub (`game.lan.hub.guests`, `Guest.placed`). Use
  `GameHost::guest(uuid)`, `guest_mut`, `index`, `conn`, `hub`/`hub_mut`, `game` (the `Game`).
  `GameHost::vanilla(|game| ...)` runs vanilla commands without our hook re-claiming them.
- **Guest fields** (`lan/guest.rs`): `conn, uuid, name, address, position, yaw, pitch, dimension, game_mode,
  permission (op level), flying, health, food, inventory, armor, offhand, selected, ender_items, xp_total,
  last_death, spawn, bed, menu, motion`.
- **Messages:** `hub.send_to(conn, &C::SystemChat(..))` (see `GameHost::send`); `ess_glue::nbt(spans)` makes
  the component. Kick: `hub.kick(conn, tag)`.
- **Teleport:** same dimension `hub.teleport(i, Some(pos))` after setting yaw/pitch; other dimension: push
  `server_travel::LevelTeleport` onto `game.level_teleports` (see `GameHost::teleport`).
- **Vanilla commands:** `Host::console_command` (level 4, feedback captured) and `player_command`.
  `/give`, `/effect`, `/attribute`, `/summon`, `/time`, `/weather`, `/item`, `/enchant`, `/xp` all exist.
- **Hook targets** (verified at the pin; see the horizon-mixins README for kinds and bindings; HEAD on small
  functions is safest: BEFORE_CALL and cancellable interior hooks refuse functions with closures or `?`):
  - chat (social): `horizon_client::lan::hub::chat::Hub::handle_chat` — never cancel at HEAD (the secure chat
    chain must advance); intercept the `broadcast_chat` call; send replacements as system chat.
  - leave: `horizon_client::game::lan_crafting::Game<'_>::lan_crafting_left(&mut self, host, g: &mut Guest)`;
    join: `horizon_client::game::dedicated::player_joined(id, name)` (the core already detects joins/quits by
    diffing the online list each tick, so you rarely need these).
  - death/respawn (tp): `horizon_client::game::lan_actions::Game<'_>::guest_die`, `guest_respawn(host, conn)`;
    `Guest.last_death` is already set.
  - packets (economy: signs/interact; items: powertools): cancellable HEAD on
    `horizon_client::game::lan_actions::Game<'_>::lan_guest_packet(&mut self, host, conn, packet: S)`
    (`S::UseItemOn`, `S::PlayerAction`); `horizon_client::game::sign_edit::Game<'_>::lan_sign_update`;
    break: `horizon_client::game::Game<'_>::break_block_as_player(&mut self, pos) -> Result<()>`.
  - command tree for tab completion (social owns): cancellable HEAD on `horizon_client::lan::hub::Hub::set_mod_commands`;
    the tree is commands.json-style JSON (`Hub::send_commands`, `lan/commands.rs`).
  - nick (social): RETURN on `horizon_client::lan::hub::Hub::player_display_name`, `horizon_client::lan::hub::display_name`;
    tab name via `PlayerInfoUpdate` action 0x20. MOTD: RETURN on `horizon_client::lan::Shared::status_json`.
  - bans (admin): HEAD on `horizon_client::game::dedicated::Game<'_>::sync_ops(&mut self, lists)` to keep the
    `Arc<Mutex<Lists>>`; a module placed in `game/dedicated.rs` (file of a `[[module]]`) sees its private items
    (`USER_CACHE`, `resolve`).
  - fly (world): RETURN on `horizon_client::lan::guest::Guest::ability_flags`; god: there is no single damage
    hook (look at `PlayerMotion::hurt` / `hurt_player_by` in `creatures.rs`); vanish: `Hub::track_entities`
    is shared by all viewers (global hide only: mark partial), tab list via `PlayerInfoUpdate` UPDATE_LISTED.
  - containers (items): `Hub::open_container(conn, kind, title, pos, slots, items)`, `Hub::open_window`; the
    vehicle-chest trick for virtual inventories (fake `BlockEntity::Chest` key, RETURN on
    `lan_actions::Game<'_>::chest_vehicle_still_valid`); workstations `lan_open_crafting`, `lan_open_station`
    with RETURN on `lan_table_valid` and the stations' validity checks.
- `[[state]]` and bridges can't target `Game<'_>` or `Guest` (generic or no private fields): keep state in your
  module (statics/`Ess::state`). Modules placed in `crates/horizon-client/src/game.rs` see `Game`'s private
  fields (`lan`, `level_teleports`, `world_root`, `spawn`, `chat_capture`...).
- Module files can't use `mod x;`, `include!` or inner attributes (`//!`, `#![...]`): use `//` comments.
